# v0.2 Jobs: design

Scope from `docs/IDEA.md`: capture every posting, move it through stages, keep the next follow-up, and compare it
with the user's criteria. Jobs is the center of Kairo: Today (v0.3), Contacts (v0.4), AI analysis (v0.6) and Metrics
(v0.9) all build on it.

Built on decisions 028 (stages and history), 029 (salaries), 030 (table view) and 031 (duplicate detection).

## Endpoints

Every route is for a signed-in user (`@Can.Anyone()`) and works on that user's rows only: another user's job answers
404, never 403, so its existence is not revealed.

| Route | Behavior |
|---|---|
| `GET /jobs` | The user's jobs. Filters: `status`, `q` (company or title). Sort: `followUp` (soonest first, empty last) or `updated` |
| `POST /jobs` | Creates a job in `to_review` (or the given status) and its first history entry. Answers with possible duplicates (decision 031) |
| `GET /jobs/:id` | One job, with its criteria match |
| `PATCH /jobs/:id` | Changes any field except `status` |
| `DELETE /jobs/:id` | Deletes the job and its history |
| `POST /jobs/:id/status` | Moves the job to another stage and records the change in the same transaction |
| `GET /jobs/:id/history` | The job's stage changes, oldest first |
| `GET /criteria` | The user's criteria, or the empty defaults |
| `PUT /criteria` | Saves the user's criteria |

Every job response includes `criteria`: for salary, remote and contract, one of `meets`, `misses`, `unknown` (the job
does not say), for salary also `not_comparable` (another currency or period), or `null` when the user set no such
criterion.

## Rules

- **Ownership in every query.** Services always filter by the current user's id; an id from the URL is never trusted
  alone. `createTwoUsers()` tests prove it for every route.
- **The admin has no bypass.** An admin's jobs are their own; they cannot read anyone else's.
- **Status changes go through one endpoint**, so no change escapes the history.
- **Validation** with zod `strictObject` schemas, as in v0.1; URLs must be `http` or `https`.

## Web screens

| Route | What |
|---|---|
| `/jobs` | Table with a tab per stage (and "all"), search, sorting by follow-up; each row shows the criteria match |
| `/jobs/new` | The capture form; shows possible duplicates after saving |
| `/jobs/[id]` | Detail: edit, change stage, history, next follow-up, delete |
| `/criteria` | The user's criteria form |

The header links to Jobs. The home page stays a placeholder: Today (v0.3) replaces it with the follow-ups due, and
until then the jobs table sorted by follow-up shows them.

## Tests

- API: unit tests for the criteria match; end-to-end tests for every route, isolation with `createTwoUsers()`, history
  written on create and on every status change, cascading deletes.
- Web: Playwright for capturing a job, moving it through stages, the follow-up, the criteria and the table filters.

## Build order

Each step is one commit. API first, then the web app.

1. API: `Job` entity, migration, create, list, read, update and delete, with isolation tests.
2. API: stages, `POST /jobs/:id/status` and the history.
3. API: next follow-up, criteria and the criteria match.
4. API: duplicate detection, `TODO(Raymundo)` (decision 031).
5. Web: jobs table with stage tabs and search.
6. Web: capture and edit forms.
7. Web: job detail with stage changes, history and follow-up.
8. Web: criteria screen.
9. Web: end-to-end tests for jobs.
10. Demo seed with fictional companies, privacy review of both repositories' history, and the switch to public
    (decision 002).
