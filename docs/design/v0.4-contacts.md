# v0.4 Contacts: design

Scope from `docs/IDEA.md`: who the user talked to at each company, and when to write again. The reminders show up in
Today next to the jobs' follow-ups and the tasks.

Built on decisions 036 (contacts and jobs), 037 (reminders), 038 (the conversation log) and 039 (the company).

## Data model

### `contacts`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key |
| `user_id` | `uuid` | FK to `users`, `ON DELETE CASCADE`, indexed. Every query filters by it |
| `name` | `text` | Required |
| `company` | `text`, nullable | Free text (decision 039) |
| `role` | `text`, nullable | Their job title, such as "Talent Partner" |
| `kind` | enum `recruiter`, `hiring_manager`, `interviewer`, `referral`, `employee`, `other`, nullable | How they relate to the search |
| `email` | `text`, nullable | |
| `phone` | `text`, nullable | Free text, as the user writes it |
| `linkedin_url` | `text`, nullable | Typed by hand, `http` or `https`. Never fetched |
| `notes` | `text`, nullable | |
| `next_follow_up_on` | `date`, nullable | When to write again (decision 037) |
| `next_follow_up_note` | `text`, nullable | What to write about |
| `created_at`, `updated_at` | `timestamptz` | |

Index on `(user_id, next_follow_up_on)`, as on jobs.

### `job_contacts`

| Column | Type | Notes |
|---|---|---|
| `job_id` | `uuid` | FK to `jobs`, `ON DELETE CASCADE` |
| `contact_id` | `uuid` | FK to `contacts`, `ON DELETE CASCADE`, indexed |
| `created_at` | `timestamptz` | |

Primary key `(job_id, contact_id)`. Both must be the same user's: the service checks it on every link (decision 036).

### `contact_interactions`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key |
| `contact_id` | `uuid` | FK to `contacts`, `ON DELETE CASCADE`, indexed. Ownership comes through the contact |
| `occurred_on` | `date` | The day of the conversation |
| `channel` | enum `email`, `linkedin`, `call`, `meeting`, `other` | Decision 038 |
| `note` | `text`, nullable | |
| `created_at` | `timestamptz` | |

## Endpoints

Every route is for a signed-in user (`@Can.Anyone()`) and works on that user's rows only: another user's contact
answers 404, never 403.

| Route | Behavior |
|---|---|
| `GET /contacts` | The user's contacts, by name. Filters: `q` (name or company), `jobId` (a job's contacts, for its page) |
| `POST /contacts` | Creates a contact. Optional `jobIds` links it at once; a job that is missing or another user's answers 400 `job_not_found`, as with tasks |
| `GET /contacts/:id` | One contact |
| `PATCH /contacts/:id` | Changes any field, including the next follow-up |
| `DELETE /contacts/:id` | Deletes the contact, its links and its conversations |
| `PUT /contacts/:id/jobs/:jobId` | Links the contact to a job; linking twice changes nothing. 204 |
| `DELETE /contacts/:id/jobs/:jobId` | Unlinks them. 204 |
| `GET /contacts/:id/interactions` | The conversations, latest first |
| `POST /contacts/:id/interactions` | Logs a conversation |
| `PATCH /contacts/:id/interactions/:interactionId` | Changes one |
| `DELETE /contacts/:id/interactions/:interactionId` | Deletes one |
| `GET /today` | Adds `contactFollowUps`: every contact with a next follow-up, with its name and company |

Each contact in a response carries its jobs (`id`, `company`, `title`, `status`) and the day of its latest
conversation (`lastInteractionOn`), so the list and the job page need no other request.

The contact follow-up actions in Today use `PATCH /contacts/:id`, as the jobs' do: **Done** clears
`nextFollowUpOn` and `nextFollowUpNote`; **Postpone** sends a new `nextFollowUpOn`.

## Web screens

| Route | What |
|---|---|
| `/contacts` | Table: name, company, kind, latest conversation, next follow-up; search |
| `/contacts/new` | The contact form. Opened from a job's page (`?jobId=`), it links the new contact to that job |
| `/contacts/[id]` | Detail: their data, their jobs (link one, unlink), the conversation log (add, edit, delete) and the next follow-up |
| `/contacts/[id]/edit` | The contact form, filled in |
| `/jobs/[id]` | Adds a **Contacts** section: the job's contacts, linking an existing one, and creating one already linked |
| `/` | Today shows contact follow-ups mixed with the rest, with **Done** and **Postpone** |

The header links to Contacts. Logging a conversation does not change the next follow-up: the user sets it.

## Rules

- **Ownership in every query**, including both ends of a link and a conversation's contact. `createTwoUsers()` tests
  prove it for every route.
- **The admin has no bypass**, as in v0.2.
- **Validation** with zod `strictObject` schemas; days are `YYYY-MM-DD`; the LinkedIn URL is `http` or `https`.
- **Contacts are other people's personal data.** They live only in the database. Tests and screenshots use fictional
  people, as everywhere else.
- **No LinkedIn automation.** The profile URL is a link the user typed; Kairo never fetches it.

## Tests

- API: end-to-end tests for every route, isolation with `createTwoUsers()` (also through `jobId`, `jobIds` and links),
  links removed with either end, conversations removed with the contact, and `GET /today` returning contact
  follow-ups.
- Web: Playwright for creating, editing and deleting a contact, linking and unlinking jobs from both pages, logging
  conversations, and the follow-up actions in Today.

## Build order

Each step is one commit. API first, then the web app.

1. API: `Contact` entity, migration, create, list, read, update and delete, with isolation tests.
2. API: links to jobs (`job_contacts`), the `jobId` filter and `jobIds` on create.
3. API: the conversation log.
4. API: contact follow-ups in `GET /today`.
5. Web: the contacts list and the create and edit forms.
6. Web: the contact detail, with its jobs and conversations.
7. Web: the Contacts section on a job's page.
8. Web: contact follow-ups in Today.
9. Web: end-to-end tests for contacts.
